# Harness vs training on a small model

A small, measured experiment on a 0.5B model. How much does a better harness recover, how much does fine tuning add, and does fine tuning change what the harness needs to fix?

## Why I ran this

Most of my engineering work has been harness work around models I could not change: Claude Code Skills at UKG, and plan validation, scoped tools and replay in MCP-X. Adaption's post [A Better Harness Can Unlock Smaller Models](https://adaptionlabs.ai/blog/a-better-harness-can-unlock-smaller-models) found the same split at 27B on legal agent tasks: the harness recovered what the model could already do, and post training added what it could not. They left the loop between the two open. I wanted to see that split myself, at a scale I can run for free, on a task where every answer can be checked.

## Setup

**Task.** Turn a request into one JSON tool call. Four tools: weather, flights, currency conversion, meetings. Requests are generated by code, so every one has an exact gold answer. Example:

> Book an hour and a half with the team this coming Friday at quarter past 3 in the afternoon.
> `{"name": "schedule_meeting", "arguments": {"date": "2026-03-06", "start_time": "15:15", "duration_minutes": 90}}`

Each argument is written in one of several phrasings ("kinds"): a date as `2026-03-15`, `March 15`, `in 3 days` or `this coming Friday`; an amount as `2500`, `2,500`, `2.5k` or `two thousand`. Errors are measured per kind.

**Model.** Qwen2.5-0.5B-Instruct, greedy decoding.

**Arms.** All scored on the same 600 held out requests.

| Arm | What changes |
|---|---|
| Plain | Nothing. One attempt. |
| Harness | Parse and schema check the reply. If it fails, send back the specific errors and allow one retry. The harness never sees the answer, so it can fix format and schema errors but not a valid wrong value. |
| LoRA, random data | Fine tune (rank 16) on N generated examples, phrasings sampled uniformly. |
| LoRA, targeted data | Same N, same recipe, but phrasings sampled in proportion to the base model's error rate on a separate 400 example probe set. |
| LoRA + harness | Each fine tuned model run through the harness. |

N is 250 and 1000. Three seeds per configuration. Training and eval sets never overlap (checked in tests).

**Cost.** Training tokens, training seconds and peak GPU memory per run; prompt plus completion tokens per request at inference, including retries.

## Limitations

- One small model and one synthetic task. Real requests are messier than four templates per tool.
- The harness has one retry and only schema feedback. A stronger harness (few shot examples, constrained decoding) would change the numbers.
- Targeting uses one round of probe errors, not an iterated loop.

## Reproduce

```bash
pip install -e ".[dev]"
pytest
bash scripts/run_all.sh          # full run, about 3 hours on a Kaggle T4
python -m hvt.report             # rebuilds results/table.md and results/accuracy.png
```

Single pieces:

```bash
python -m hvt.taskgen                                             # print sample requests
python -m hvt.evaluate --mode harness --limit 50 --out results/smoke/harness
```

## Layout

```
hvt/tools.py      tool schemas, system prompt, parser and validator (no gold access)
hvt/taskgen.py    seeded request generator with exact answers
hvt/scoring.py    exact match scoring and failure taxonomy
hvt/harness.py    plain and validate+retry runners
hvt/targeting.py  probe errors to sampling weights
hvt/data.py       fixed eval/probe sets, training sets
hvt/train.py      LoRA SFT loop that reports its own cost
hvt/evaluate.py   score one arm
hvt/report.py     table and chart
```
